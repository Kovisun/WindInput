# 用户分库与外部编辑

状态：草案（2026-10-16），待维护者审阅。

## 1 目标

- **用户分库**：用户把自己的词表分成多个文件，各自开关。新造的词仍进主用户词库（维护者定：只读分库，不做多个可写库）。
- **外部编辑**：设置里可以直接打开数据目录或某个数据文件，用编辑器批量改，改完程序接着用，不再靠「导出 → 改 → 导入」。
- 导入导出格式的统一另起一份设计，本文只在 §5 记它与本文的接口。

## 2 现状（2026-10-16 核对）

- 用户词只认 `data/<数据方案>/user.dict.yaml` 一个文件：路径、`dict.reload` 白名单、引擎的 (target, schema) 绑定、日志记录都只有这一维（`wind-store/src/store.rs:431`、`user_words.rs:603`、`wind-userdata/src/record.rs:12`）。
- 扩展词库已经是「用户自放、可开关」的词库：`[[dictionary_dirs]]` 或默认 `<主词库目录>/ext` 下的 `*.dict.yaml` 在读方案时自动登记（`inject_dir_dicts`，`wind-engine/src/manager.rs:7196`），id 为 `dir:<相对路径>`，出厂关，开关按方案存在 `schema_overrides/<方案>.toml`（`schema.setDictEnabled`）。它是系统层：码表按 `base_order` 排在主库后，拼音并进系统词库的分层缓存按权重比。
- 扩展词库在设置里只出现在「方案管理 → 扩展词库」，只能开关；新增要点「打开目录」放文件、重开窗口；改文件内容后 `dict.reload` 不管，要等方案重建。
- 外部改 `user.dict.yaml` 已有基础：启动 / 切方案 / 配置重载时按内容指纹同步，`dict.reload` 可手动触发；写回前复核指纹，不一致就放弃本轮、退避重试。剩余风险是**编辑器开着旧内容时程序写回、用户随后保存**，程序写进去的行被盖掉，之后以文件为准，这些词就丢了。
- 设置端已有 `open_with_default_app`（`wind-setting/src/open_external.rs:14`），字符类有一套「导出 → 外部编辑 → 试算 → 加载」的对话框可作样板。

## 3 用户分库

### 3.1 定义

`data/<数据方案>/` 下除保留名外的每个 `*.dict.yaml` 是一个用户分库。保留名：`user`、`shadow`、`temp`、`draft`（以及将来引擎占用的名字，集中在一张表里）。格式与 `user.dict.yaml` 相同（Rime 词库，列 `text, code, weight`，可省权重）。

### 3.2 复用扩展词库机制，不另建一套

P2c 曾裁定「用户分库并入扩展词库目录，不另建机制」，理由是两处入口、两处配置。本设计保留「不另建机制」，只是给扩展词库**多一个来源目录**：

| | 扩展词库（现有） | 用户分库（新增） |
|---|---|---|
| 位置 | `schemas/<主词库目录>/ext` 等 | `data/<数据方案>/` |
| 面向 | 方案作者、随包细胞词库 | 用户自己的词表 |
| id | `dir:<相对路径>` | `user:<文件主名>` |
| 档位 | 系统层，排在主库后 | 排在系统库之前，与用户词同档 |
| 出厂 | 关 | 开（用户自己放进来的，默认就要用） |
| 备份 / 外部编辑 | 随 `schemas/` 整树 | 随 `data/`，与用户词一起 |

发现、编译缓存（按内容指纹，没变不重编）、开关存储（`schema.setDictEnabled` → `schema_overrides`）、启停生效路径全部沿用。与 P2c 的差别只在「用户的东西放在用户数据目录里」：备份、外部编辑、文档里讲「你的数据都在 `data/`」都更顺。

- **档位**：码表用 `base_order = -3`（与用户层相同，`wind-dict/src/layer.rs:150`）。拼音的扩展库并进系统词库分层缓存、按权重比，分库同样处理；无权重的分库行取方案的 `default_weight`。
- **开关按方案**：全拼与双拼共用 `data/pinyin/` 的文件，开关各自独立，与扩展词库的现行语义一致。
- **删词**：界面里删分库的一条 = 改该文件（按行补丁 + 指纹复核 + 原子替换），随后失效相关方案；不走 Shadow。Shadow 仍可对任何词置顶 / 删除。
- **改了文件怎样生效**：`dict.reload` 认 `data/<数据方案>/*.dict.yaml`，对分库文件做「失效用到该数据方案的方案」。指纹没变就不重编，代价是一次方案重建。

### 3.3 设置端

词库窗每个方案加一个子标签「词库」：

- 一张表列出这个方案的全部词库：主词库、扩展词库、用户分库，每行有开关、条目数、来源（系统 / 扩展 / 我的）。方案管理里的「扩展词库」一节保留，改为跳到这里。
- 用户分库支持：新建（空文件带表头）、从文件导入为新分库（第三方格式先转换成 Rime 格式再落盘）、重命名、删除（二次确认）、打开文件、打开所在目录。
- 选中一个分库看条目：分页、搜索、删除单条。添加和修改走外部编辑（§4）或加到主用户词库。

### 3.4 不做

- 多个可写分库、新词写入指定分库。
- 把分库条目移动到主用户词库或另一个分库（以后要做再议）。

## 4 外部编辑

### 4.1 可编辑的文件

`data/<数据方案>/user.dict.yaml`、`shadow.dict.yaml`、用户分库，`data/phrases.dict.yaml`、`quick_format.toml`、`common_chars.yaml`、`charsets/*.yaml`。

不开放：`temp` / `draft` / `freq` / `assoc` / 补全 / 统计。这些由程序高频写入，人工编辑价值低、冲突风险高，入口上不提供（文件本身不加锁，用户硬改照现有同步规则处理）。

### 4.2 编辑会话

```
设置端「编辑文件」 → data.beginEdit {file}
   core：该文件对应的目标先折回一次（文件里有全部数据），然后暂停它的写回
   返回绝对路径 → open_with_default_app
设置端显示编辑条「正在编辑 xxx  [完成并加载] [放弃]」
用户在编辑器里改、保存
「完成并加载」 → data.endEdit {file}
   core：按文件同步（与 dict.reload 同一路径）→ 恢复写回 → 返回解析问题（坏行号与原因）
```

- 编辑期间照常打字、造词：新写入留在日志和 delta 里，查询不受影响；恢复写回后按行补丁落到用户改过的文件上，不会丢。这是会话相对「直接打开文件」的全部价值。
- 小表（短语、Shadow、快捷格式、常用字、字符类）编辑期间，界面里对同一张表的修改先挡住，提示「正在外部编辑」。
- **租约**：会话记在 core 内存里，设置进程退出或 2 小时无动作自动结束（按「完成并加载」处理）；core 重启后不存在会话，所以不会卡死写回。
- 解析问题：坏行跳过并计数、整份坏则隔离不折回，沿用 §2.5 的统一策略；`endEdit` 把问题列表带回，编辑条直接展示，并提供「再次打开修改」。

### 4.3 不走会话的直接编辑

用户用资源管理器自己打开文件改也行，沿用现有规则：写回前复核指纹，启动 / 切方案 / 配置重载时同步。词库窗工具栏加「重新加载」（调 `dict.reload`），以及「打开数据目录」。文档里写明：编辑器开着文件时，别让程序写回之后再保存旧内容——推荐用「编辑文件」入口。

## 5 与格式统一的接口

格式统一另立设计，本文只定一个方向：**自有交换格式就是 `data/` 下的真源文件**。用户分库是落地的第一步——「导入为分库」的结果就是一个真源格式文件，导出一个分库就是拷贝它。备份包现在逐表重新序列化（wdict / jsonl），用户分库在本设计里先按文件原样进包（`data/<数据方案>/<名>.dict.yaml`，type `user_dict_file`），整个备份改成「打包 `data/`」放到格式统一那一份里做。

## 6 阶段

| 阶段 | 内容 |
|---|---|
| E1 | 外部编辑：`data.beginEdit` / `data.endEdit`、写回暂停与租约、小表编辑互斥；设置端「编辑文件」「打开数据目录」「重新加载」与编辑条 |
| E2 | 用户分库 core：`data/<数据方案>/` 作为扩展词库来源（id、档位、出厂开）、`dict.reload` 认分库文件、分库增删改 RPC、备份带分库文件 |
| E3 | 用户分库设置端：词库窗「词库」子标签、方案管理入口改跳转、导入为分库 |
| E4 | 文档站：用户分库、外部编辑；用户数据存储设计 §4 / §10 P2c 改写 |
